## Temuan Kritis

### K1 — Mapping kode `updatePrinterState()` Sunmi salah
Dokumentasi di `IWoyouService.aidl` sendiri: `1 normal, 2 memperbarui status, 3 gagal membaca status, 4 kertas habis, 5 overheat, 6 cover terbuka, 7 cutter abnormal, 8 cutter pulih, 505 printer tidak terdeteksi` (+`507` upgrade firmware gagal, tabel resmi Sunmi). Kode lama memetakan **3 → kertas habis** dan membiarkan **4 → unknown**, dan test lama justru mengunci perilaku ini.

Dampak: di perangkat Sunmi asli, kondisi kertas habis sungguhan tidak pernah memblokir cetak, dan hasilnya dilaporkan `PrinterOk`.

> **Koreksi setelah device testing 01:** dugaan awal bahwa bug ini juga menjelaskan temuan lapangan "Xcheng membaca cache basi" **terbantah**. Di perangkat Xcheng O1, `updatePrinterState()` memang selalu mengembalikan 1, dengan maupun tanpa kertas. Perbaikan mapping tetap benar untuk Sunmi asli, tapi deteksi kertas di Xcheng butuh `PrinterBackendXcheng` (lihat bagian "Hasil device testing 01").

Perbaikan: fungsi murni `sunmiStateToStatus()` dengan tabel lengkap. Kode transien (2, 3, 8, 9, tak dikenal) → `unknown`, jadi tidak memblokir.

### K2 — Thread baca ESC/POS mati diam-diam
`ConnectedThread.run()` memanggil `readSink.success(...)` langsung. App konsumen tidak pernah subscribe `onRead()`, sehingga `readSink == null` dan NPE memicu `break`. Pemicunya adalah byte apa pun yang tidak diminta: XON/XOFF, respons `DLE EOT` yang datang telat, atau byte ke-2 dst. di jalur status. Selain itu, `EventSink` dipanggil dari background thread, padahal Flutter mewajibkan main thread.

Dampak: setelah thread mati, **semua** query status timeout (1,5 dtk) → `unknown`. Pre/post-check jadi tidak berfungsi tanpa terlihat, dan tiap cetak kena tambahan latensi ±3 dtk.

Perbaikan:
- `readSink` dibuat `volatile`, dipanggil lewat main `Handler`, dan byte dibuang bila tidak ada listener.
- Loop menangkap semua exception.
- Koneksi dibersihkan di `finally`.

### K3 — Koneksi basi tidak pernah dibersihkan
`connectedThread` (static) hanya di-null-kan oleh BroadcastReceiver, dan receiver itu hanya terdaftar selama ada yang listen `onStateChanged()` (app konsumen tidak listen). Receiver juga meng-null-kan untuk ACL disconnect perangkat **mana pun** tanpa menutup socket.

Dampak: printer dimatikan lalu dinyalakan → `isConnected` tetap `true`, write gagal, dan `connect()` → `"already connected"` sampai app di-restart.

Perbaikan:
- `AtomicReference<ConnectedThread>`. Thread baca membersihkan dirinya sendiri (`compareAndSet(this, null)` + tutup socket) saat socket mati.
- `isConnected` memeriksa thread hidup + socket tersambung.
- `connect()` ke alamat yang sama selagi hidup bersifat idempoten.
- Receiver mencocokkan alamat perangkat dan menutup socket.

### K4 — Header raster `GS v 0` rusak untuk gambar ≥256 px
`Utils.decodeBitmap` menulis dimensi sebagai string hex big-endian tanpa padding. Contoh: tinggi 300 → `"12c"+"00"` → byte `12 C0` → printer membaca 49.170 baris. Piksel transparan juga dicetak hitam.

Dampak: `printImage`/`printImageBytes`/`printQRcode` (API lama) mencetak sampah untuk gambar tinggi.

Perbaikan: `RasterImageEncoder` (Java murni, dites JUnit):
- header little-endian
- pita ≤128 baris
- padding putih
- alpha dikomposit ke putih

## Temuan Tinggi

- **T1 — Hasil cetak Sunmi.**
  - Masalahnya: doc `ICallback.onRunResult` menyatakan callback itu *tidak* menunjukkan hasil kerja printer, dan hasil sungguhan hanya ada di mode transaksi. Kode lama menganggap timeout callback (3 dtk) sebagai sukses. API yang benar (`exitPrinterBufferWithCallback` → `onPrintResult`, 0 = sukses) sudah ada di AIDL tapi tidak dipakai.
  - Perbaikan: `printTransaction` native (enter buffer → bitmap → `lineWrap` → exit dengan callback) menghasilkan outcome `printed`/`failed`/`unknown`.
    - Firmware tanpa callback → `unknown` + post-check.
    - Setelah satu kali timeout, bridge langsung memakai commit polos supaya jeda hanya terjadi sekali per sesi.
- **T2 — Validasi `DLE EOT`.**
  - Masalahnya: semua respons `DLE EOT n` punya pola bit tetap `(b & 0x93) == 0x12`, dan byte lain dulu ikut terbaca sebagai status.
  - Perbaikan:
    - Native memindai buffer untuk byte sah pertama (`EscPosStatus`).
    - Dart memakai `PrinterStatus.tryFromOfflineStatusByte`.
- **T3 — ANR.** Semua write ESC/POS kini dijalankan di satu executor serial, bukan platform thread.
- **T4 — Race connect.**
  - Native: flag `connecting` → `connect_in_progress`.
  - Dart: `PrinterBackendEscpos.connect` single-flight.
- **T5 — Kunci permanen.** `PrintJobGate`: bila pekerjaan native masih belum selesai 30 dtk setelah timeout, `onStuck` dipanggil (ESC/POS: `disconnect()` menutup socket agar write yang macet terlepas) dan kunci dilepas.
- **T6 — Lebar renderer.** `ArgumentError` untuk lebar ≤0 atau bukan kelipatan 8.
- **T7 — Binding Sunmi.**
  - `volatile`, `onBindingDied` → bind ulang, `onNullBinding` ditangani.
  - Polling connect diperpanjang dari 1 dtk menjadi ±3 dtk (boot dingin).
- **G1 — `PrintJobGate`.**
  - Masalahnya: `Future.sync(job)` meneruskan `Future<Never>` milik job yang langsung melempar, lalu `timeout(onTimeout:)` melempar `TypeError`.
  - Perbaikan: job dibungkus fungsi `async`. Bug ini ditemukan oleh test baru.

## Backlog (Sedang/Rendah — belum diperbaiki)

- **S1 — Post-check ESC/POS ≠ "sudah tercetak".** `DLE EOT` dijawab saat byte diterima printer, bukan setelah dicetak. Opsi: barrier `GS r 1` (diproses berurutan setelah data sebelumnya) + polling dengan timeout. Butuh verifikasi hardware printer yang dipakai.
- **S2 — Permission manifest terlalu luas untuk plugin lintas app.**
  - Manifest: `BLUETOOTH_ADVERTISE` (tidak dipakai), lokasi, `BLUETOOTH`/`BLUETOOTH_ADMIN` tanpa `maxSdkVersion="30"`, `BLUETOOTH_SCAN` tanpa `usesPermissionFlags="neverForLocation"`.
  - `hasRequiredBluetoothPermissions()` mensyaratkan SCAN+FINE_LOCATION padahal connect cukup `BLUETOOTH_CONNECT`, dan NPE bila `activity == null`.
  - Perlu keputusan konsumer (rencana active discovery).
- **S3 — `pendingResult` tertimpa.** Terjadi bila `getBondedDevices` dipanggil saat dialog izin masih terbuka, sehingga Future pertama menggantung.
- **S4 — Siklus hidup plugin.**
  - `detach()` membocorkan receiver/handler read channel.
  - Method channel ESC/POS hanya terdaftar saat ada Activity (engine tanpa Activity → `MissingPluginException`).
- **S5 — Fallback tanpa timeout.** `createRfcommSocket(1)` tidak punya timeout.
- **S6 — Pratinjau ≠ cetakan.** `Receipt.toPlainText` (kanan-rata) berbeda dari raster (`label: value`), dan `Receipt.width` diabaikan renderer.
- **S7 — Build lama.**
  - `PrinterCommands.SELECT_FONT_A = {20,33,0}` (seharusnya `27`), tidak dipakai.
  - `buildscript` AGP 3.5.4, Java 1.8, dan `AsyncTask` (deprecated) usang.
- **S8 — `paperNearEnd`.** Tambahkan field `PrinterStatus.paperNearEnd` (ESC/POS `DLE EOT 4`, iMin kode 8) sebagai peringatan yang tidak memblokir. Dikerjakan di fase 2 bersama iMin.
- **S9 — Ekosistem Sunmi.** `sunmi_printer_plus` v4 meninggalkan AIDL demi SDK gradle, dan Sunmi menyediakan PrinterX SDK (`com.sunmi:printerx`). Rekomendasi: **tetap AIDL** (satu-satunya antarmuka yang diimplementasikan klon seperti Xcheng). PrinterX dievaluasi terpisah bila nanti ada kebutuhan fitur yang tidak ada di AIDL.

## Hasil device testing 01 (24 Sep 2026)

Perangkat: Xchengtech O1, Android 9, servis printer `com.xcheng.printerservice` v1.1.12 (menyediakan AIDL kompatibel Sunmi + antarmuka native Xcheng), printer virtual Bluetooth `RPPInnerPrinter`. Diuji lewat harness `integration_test` di luar repo, dengan dan tanpa kertas.

| Item | Hasil |
|---|---|
| K3 (connect ulang idempoten), T4 (connect paralel → 1 percobaan) | ✅ Lulus |
| T3 (write 60 KB tidak memblokir platform thread) | ✅ Latensi panggilan lain 4–10 ms |
| K4 (gambar 389 px lewat `printImageBytes`) | ✅ Tercetak utuh sampai akhir |
| K1 (mapping status Sunmi) | ⚠️ Benar menurut spesifikasi, tapi servis Xcheng selalu mengembalikan 1 (normal), termasuk tanpa kertas |
| T1 (hasil transaksi Sunmi) | ⚠️ Servis Xcheng tidak pernah memanggil callback transaksi. Awalnya cetak pertama tertunda 12 dtk → diperbaiki (klon terdeteksi, 274 ms) |
| `DLE EOT` di `RPPInnerPrinter` | ⚠️ Tidak dijawab. Awalnya +3 dtk per cetak → diperbaiki (hanya cetak pertama) |
| Kertas habis | ❌ Backend default (Sunmi/ESC-POS) tidak bisa mendeteksinya di perangkat ini, dan data yang dikirim menumpuk lalu tercetak begitu kertas dipasang |
| Sensor native Xcheng `printerPaper()` | ✅ `false` tanpa kertas, `true` dengan kertas |
| Callback native Xcheng `printBitmap` | ✅ `onStart`/`onComplete` ~60 ms saat ada kertas; tidak ada callback tanpa kertas |

Tindak lanjut: backend `PrinterBackendXcheng` (`PrinterVendor.innerXcheng`) untuk perangkat Xcheng, terpilih otomatis untuk instalasi baru lewat `detectBuiltInPrinterVendor()` (Xcheng → Sunmi → Bluetooth), dengan fallback ke Sunmi bila antarmuka native Xcheng tidak bisa terhubung. Tidak ada SDK Xcheng resmi yang bisa diunduh: integrasi resminya adalah file AIDL yang dibagikan OEM, dan urutan method 1–17 terverifikasi identik antara bytecode servis perangkat uji dan AIDL OEM Positivo L300.

Verifikasi backend Xcheng di perangkat yang sama:
- Tanpa kertas: cetak ditolak "Kertas printer habis." tanpa data terkirim, dan tidak ada struk menumpuk saat kertas dipasang kembali.
- Dengan kertas: cetak dikonfirmasi `onComplete` dalam 0,3–0,8 dtk.
- Deteksi boot: O1 terdeteksi `innerXcheng` (282 ms).
- Fallback: antarmuka Xcheng yang disimulasikan tidak menjawab → pindah ke Sunmi (256 ms) dan tetap mencetak.

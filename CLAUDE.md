# CLAUDE.md

File ini berisi panduan untuk Claude Code (claude.ai/code) saat bekerja dengan kode di repository ini.

## Tentang project ini

Ini adalah fork internal dari paket pub.dev `blue_thermal_printer` (upstream: `kakzaki/blue_thermal_printer`), dikelola di `Bahana-Cipta-Technology/blue_thermal_printer`. API lama (`lib/blue_thermal_printer.dart`, class `BlueThermalPrinter`) **sama sekali tidak mengonsumsi SDK vendor/pabrikan printer apa pun** — semuanya dibangun dari komponen generik/universal: API Bluetooth Classic bawaan Android (`BluetoothSocket` lewat UUID SPP standar `00001101-0000-1000-8000-00805F9B34FB`) untuk koneksi, dan byte command ESC/POS (protokol terbuka, tidak terikat merek printer manapun) yang ditulis manual untuk semua data yang dikirim ke printer. Bitmap QR di-generate pakai ZXing, itu pun cuma buat rendering lokal, bukan komunikasi ke printer. Pertahankan desain API lama ini apa adanya (jangan sisipkan SDK vendor ke `BlueThermalPrinterPlugin.java`/`BlueThermalPrinter` yang sudah ada).

> **Arah baru (lihat juga bagian "API umum lintas vendor" di bawah):** repo ini sekarang jadi *source of truth* multi-vendor bagi semua app Bahana-Cipta-Technology yang butuh printer thermal — bukan lagi cuma ESC/POS Bluetooth generik. SDK vendor (Sunmi built-in printer jadi yang pertama, sudah produksi) ditambahkan sebagai implementasi baru di belakang kontrak `PrinterBackend`, **bukan** disatukan ke kode ESC/POS/Bluetooth yang sudah ada — tiap vendor tetap terisolasi di modul/folder native-nya sendiri (lihat konvensi `vendor/<nama>/` di bagian Arsitektur) supaya build, test, dan siklus hidup satu vendor tidak terikat ke vendor lain. Keputusan ini sengaja mengubah batasan lama di paragraf sebelumnya (yang melarang SDK vendor sama sekali) — alasannya: semua app konsumen plugin ini butuh akses SDK vendor yang sama, jadi mendefinisikan kontraknya sekali di sini menghindari duplikasi/drift antar app.

Repo ini dipakai app `parkways_valet` (Flutter) lewat **git submodule + `path:` dependency** (bukan dipublish ke pub.dev). Migrasi ke kontrak baru `PrinterBackend` (lihat bagian di bawah) **sudah selesai** -- app konsumen sekarang mengimpor `package:blue_thermal_printer/printer_backend.dart` saja, tidak lagi menyentuh `blue_thermal_printer.dart` (API lama) secara langsung di mana pun. API lama tetap dipertahankan di repo ini apa adanya untuk kompatibilitas mundur (dipakai secara internal oleh `PrinterBackendEscpos`, lihat di bawah), bukan karena masih dikonsumsi langsung.

## API umum lintas vendor (`PrinterBackend`)

`lib/printer_backend.dart` adalah barrel export kontrak baru, jadi API utama yang dipakai app konsumen (API lama `blue_thermal_printer.dart` tetap dipertahankan apa adanya untuk kompatibilitas mundur, tidak dihapus). Isinya:

- `PrinterBackend` (`lib/src/printer_backend.dart`) — satu interface yang menyatukan pemasangan/koneksi perangkat *dan* pengiriman cetak (sengaja digabung, bukan dipisah seperti draf awal `PrinterService`/`PrinterConnectionService` di app konsumen), supaya backend tanpa konsep pemasangan (mis. printer bawaan) tidak perlu jawaban stub yang menyesatkan untuk method pemasangan — lihat getter `requiresPairing`.
- `PrinterDevice`, `PrinterStatus`, `Receipt`/`ReceiptLine` (`lib/src/`) — tipe data pendukung, netral terhadap vendor maupun app konsumen. `PrinterStatus.problemMessage` memetakan `hasPaper`/`coverClosed`/`hasError` jadi satu pesan Indonesia siap tampil, dipakai bersama oleh kedua implementasi di bawah supaya pesan galat konsisten lintas vendor.
- `PrinterResult`/`PrinterOk`/`PrinterErr`/`PrinterFailure` (`lib/src/result.dart`) — tipe hasil operasi milik plugin ini sendiri, terpisah dari `Result`/`Failure` app konsumen mana pun (plugin generik lintas app, tidak boleh tahu taksonomi galat satu app tertentu).
- `PrinterVendor` + `createPrinterBackend` (`lib/src/printer_vendor.dart`) — *source of truth* vendor mana saja yang plugin ini dukung, plus factory yang membangun instance `PrinterBackend` konkretnya. Ini yang dipakai app konsumen untuk memilih backend (bukan mendefinisikan enum vendor sendiri) — lihat bagian "Menambah vendor baru" di bawah.

**Status saat ini: kontrak + dua implementasi produksi, sudah dipakai app konsumen.**
- `PrinterBackendEscpos` (`lib/src/printer_backend_escpos.dart`) — membungkus `BlueThermalPrinter` (API lama) untuk printer Bluetooth generik lewat ESC/POS. `_send()` melakukan pre-check status sebelum menulis, lalu post-check setelah menulis (`checkStatus()`, ESC/POS `DLE EOT 2`) -- kalau post-check melaporkan masalah, tulis satu reset buffer tambahan (`ESC @`, byte `[27, 64]`) sebagai best-effort sebelum melaporkan galat ke pemanggil.
- `PrinterBackendSunmi` (`lib/src/printer_backend_sunmi.dart`) — printer bawaan lewat AIDL kompatibel Sunmi/Woyou. Native-nya terisolasi total di `android/src/main/java/id/kakzaki/blue_thermal_printer/vendor/sunmi/` (`SunmiPrinterBridge.java`, `SunmiPrinterChannel.java`, method channel `blue_thermal_printer/sunmi`, terpisah dari channel API lama `blue_thermal_printer/methods`), tidak menyentuh `BlueThermalPrinterPlugin.java` sama sekali. Selain `bind`/`unbind`/`updateState`/`printBitmap`, ada `enterBuffer`/`exitBuffer` (transaksi buffer printer, best-effort -- gagal di sini TIDAK PERNAH menggagalkan cetakan yang sebenarnya berhasil, karena API ini belum diverifikasi didukung semua vendor clone) yang mengapit `printBitmap` di `_send()`. Kode native ini fork dari `sunmi_printer_plus` (lihat `LICENSE-sunmi_printer_plus` di folder yang sama).

**Temuan penting dari pengujian hardware nyata (device Xchengtech, klon AIDL Sunmi lewat `com.xcheng.printerservice`):** `updatePrinterState()` yang dipanggil "dingin" (sebelum `printBitmap()`) bisa membaca **cache basi**, bukan sensor langsung -- status kertas fisik yang sungguhan baru ter-update lewat proses internal `printBitmap()` itu sendiri, dengan tunda tidak konsisten (pernah terukur sampai 34+ detik). Tiga lapisan pertahanan di atas (pre-check, buffer-guard, reset defensif) tetap dipertahankan karena bermanfaat untuk hardware yang berperilaku baik, tapi **tidak menjamin** mendeteksi kasus vendor se-buggy ini -- lihat mitigasi UI-level yang diambil app konsumen (halaman cetak struk tidak lagi mengklaim "sukses" berdasarkan `PrinterOk` semata) sebagai konsekuensi dari temuan ini.

### Menambah vendor baru (mis. Epson, PAX, iMin)

Pola yang sudah dipakai (`PrinterBackendSunmi`) jadi cetakan untuk vendor berikutnya:
1. Native: modul terisolasi baru di `android/.../vendor/<nama>/`, method channel sendiri (`blue_thermal_printer/<nama>`), tidak menyentuh kode vendor lain.
2. Dart: class baru `PrinterBackend<Nama>` di `lib/src/`, implementasi `PrinterBackend` sepenuhnya (termasuk pre-check status kalau SDK vendor menyediakannya).
3. Daftarkan di `PrinterVendor` (`lib/src/printer_vendor.dart`) -- satu nilai enum baru plus satu case di `createPrinterBackend`, dijaga *exhaustive* oleh compiler Dart supaya tidak ada tempat lupa di-update yang lolos diam-diam.
4. Test dengan constructor-injected fakes (pola `printer_backend_sunmi_test.dart`/`printer_backend_escpos_test.dart`), lalu verifikasi behavior native ke hardware fisik lewat app konsumen (`flutter build apk --debug`) -- `flutter test` di repo ini tidak bisa memverifikasi hardware sungguhan.

Sebelum mem-fork SDK vendor manapun: cek dulu lisensi source yang jadi referensi (community plugin pub.dev sering MIT, boleh dipakai sebagai titik awal fork) dan **jangan** langsung menambah `dependency:` ke package pihak ketiga di `pubspec.yaml` -- pola repo ini adalah isolasi native per vendor di dalam plugin sendiri (lihat poin 1), bukan menumpuk dependency eksternal yang siklus hidup/maintenance-nya di luar kendali kita.

**Dukungan platform pada praktiknya cuma Android.** `ios/Classes/SwiftBlueThermalPrinterPlugin.swift` dan versi macOS-nya itu cuma stub registrasi yang mengabaikan `call.method` sepenuhnya — apa pun method yang dipanggil, dia selalu balikin string versi device. Artinya manggil apa pun (`isOn`, `connect`, dst) di iOS/macOS bakal balikin `String` padahal yang diharapkan `bool`/list/dst, dan bakal error/cast exception di sisi Dart. Anggap iOS/macOS **tidak fungsional** — tabel platform di README (yang menandai semua platform selain Android sebagai tidak didukung) itu yang benar. `pubspec.yaml` tidak lagi mendaftarkan plugin class untuk `ios`/`macos` (dihapus supaya metadata tooling konsisten dengan status "tidak fungsional" ini); kalau dua platform itu suatu saat diimplementasikan sungguhan, daftarkan lagi entrinya di `flutter.plugin.platforms`.

Verifikasi behavior native (koneksi, tulis byte ke printer sungguhan) tetap harus lewat build app konsumen (`flutter build apk --debug` di `parkways_valet`) lalu tes ke printer fisik — karena Bluetooth Classic maupun AIDL vendor gak bisa dites di lingkungan VM `flutter test` maupun target desktop Linux.

## Arsitektur

Satu `MethodChannel` (`blue_thermal_printer/methods`) untuk semua pemanggilan request/response, plus dua `EventChannel`: `.../state` (broadcast adapter Bluetooth + status ACL connect/disconnect, diekspos lewat `onStateChanged()`) dan `.../read` (byte yang dibaca balik dari `InputStream` printer, diekspos lewat `onRead()`). Sisi Dart (`lib/blue_thermal_printer.dart`) itu singleton (`BlueThermalPrinter.instance`), bukan class static murni.

Semua logic native ada di satu file: `android/src/main/java/id/kakzaki/blue_thermal_printer/BlueThermalPrinterPlugin.java` (satu `switch` besar berdasarkan `call.method` di dalam `onMethodCall`), plus dua helper kecil — `PrinterCommands.java` (konstanta byte ESC/POS mentah: align, feed, potong kertas, buka laci kasir) dan `Utils.java` (konversi bitmap → raster ESC/POS buat cetak gambar/QR).

Model threading yang perlu diperhatikan kalau mau menyentuh kode native:
- `connect`/`disconnect` jalan lewat `AsyncTask.execute` (background thread), dijaga satu field `static ConnectedThread connectedThread` — artinya cuma ada **satu** koneksi aktif yang dilacak di level class, bukan per instance plugin.
- Semua method lain (`write`, `writeBytes`, `printCustom`, dst) jalan **synchronous di platform/UI thread** di dalam `onMethodCall` — channel ini tidak didaftarkan pakai `BinaryMessenger.TaskQueue`. Printer yang lambat/gak respon pas nulis bisa bikin UI thread app konsumen ikut macet. `queryPrinterStatus` adalah pengecualian yang disengaja: ia jalan lewat `AsyncTask.execute` (background thread) karena harus menunggu respons async hingga `STATUS_QUERY_TIMEOUT_MILLIS`.
- `ConnectedThread.run()` loop `inputStream.read()` dan kirim tiap byte ke `EventChannel` read; kalau gak ada yang dengerin (`readSink == null`), `NullPointerException` yang muncul bakal diam-diam mematikan thread baca itu selamanya (di-catch, loop-nya langsung `break`).
- `queryPrinterStatus` (ESC/POS `DLE EOT n`, dipetakan dari `PrinterCommands.TRANSMIT_DLE_*`) butuh menangkap satu byte respons yang datang lewat `InputStream` yang sama dengan yang terus-menerus dibaca `ConnectedThread.run()` di atas. Solusinya: mailbox satu slot (`ArrayBlockingQueue<Byte> statusResponseMailbox` + flag `awaitingStatusResponse`) di dalam `ConnectedThread` — di-*arm* lewat `armStatusRequest()` sebelum menulis command query, dan `run()` sendiri yang mengalihkan byte pertama yang datang ke mailbox (bukan `readSink`) selama flag itu aktif, alih-alih membuka thread pembaca kedua di atas socket yang sama. `ConnectedThread.write(byte[])` sekarang `synchronized` supaya query status (thread background) dan print job (platform thread) tidak saling rebutan `OutputStream`.

## Known issues

**Sudah diperbaiki di fork ini** (lihat riwayat commit — perbaikan ini wajib supaya plugin bisa dipakai sama sekali oleh konsumer Dart 3.x/AGP modern, atau buat menutup bug correctness yang nyata):
- `environment.sdk` sebelumnya `>=2.12.0 <3.0.0`, gak cocok sama app Flutter modern manapun; dinaikkan ke `<4.0.0`.
- `android/build.gradle` gak punya `namespace` AGP (wajib buat AGP 8+) dan `compileSdkVersion`-nya masih 31, yang bikin gagal di pengecekan AAR-metadata terhadap versi AndroidX transitif modern; keduanya sudah dinaikkan (`compileSdkVersion 36`).
- Cabang permintaan izin Android 12+ di `getBondedDevices()` pakai `requestCode` hardcode `1`, padahal `onRequestPermissionsResult` cuma cocok sama `REQUEST_COARSE_LOCATION_PERMISSIONS` (`1451`) — `Result` yang pending gak pernah ke-resolve, jadi percobaan pertama grant izin di API 31+ hang selamanya. Sekarang kedua cabang pakai request code yang sama.
- Ditambahkan `isPermissionBluetoothGranted` (native `hasRequiredBluetoothPermissions()` + getter Dart) — cara cek status izin tanpa efek samping memicu dialog permintaan izin, sesuai kebutuhan konsumer sebelum mencoba `connect()`.
- `com.android.support:multidex` (gak dipakai, dari grup support-library pre-AndroidX yang sudah *frozen*) sudah dihapus; `androidx.appcompat`, `com.google.zxing:core`, dan `com.journeyapps:zxing-android-embedded` sudah dinaikkan ke versi terbaru.
- `ConnectedThread.write(byte[])` dulu menelan `IOException` secara internal (cuma `printStackTrace()`, gak dilempar lagi), jadi `writeBytes`/`write`/`print*` di plugin ini manggil `result.success(true)` **tanpa syarat**, bahkan pas penulisan fisik ke socket-nya gagal. Sekarang `write(byte[])` mengembalikan `boolean` dan tiap pemanggil (semua method yang menulis ke printer) memeriksa hasilnya lewat helper `writeOrFail(...)`, mengembalikan `result.error("write_error", ...)` kalau tulis fisik gagal.
- `onRequestPermissionsResult` dulu cuma cek `grantResults[0]`, bukan seluruh array — grant sebagian (misal `BLUETOOTH_SCAN` diizinkan tapi `BLUETOOTH_CONNECT` ditolak) tetap dianggap granted penuh. Sekarang mensyaratkan semua elemen `grantResults` granted.
- Dulu gak ada timeout di sekitar pemanggilan blocking `socket.connect()`; device yang gak respon bisa bikin percobaan connect hang tanpa batas waktu. Sekarang dibungkus `ExecutorService`/`Future.get(CONNECT_TIMEOUT_MILLIS, ...)` (12 detik) yang menutup socket dan mengembalikan `result.error("connect_timeout", ...)` kalau kelamaan.
- Dulu gak ada fallback reflection ke `createRfcommSocket(1)` (channel 1) pas socket RFCOMM secure standar gagal — workaround yang dikenal luas di ekosistem Android BT Classic buat bug "read failed, socket might closed" yang muncul di sejumlah kombinasi device/printer. Sekarang dicoba otomatis (`attemptFallbackConnect`) begitu percobaan standar melempar exception (bukan saat timeout).
- File test bawaan `test/blue_thermal_printer_test.dart` dulu gagal kalau dijalankan (`setMockMethodCallHandler` dipanggil tanpa `TestWidgetsFlutterBinding.ensureInitialized()` duluan, dan channel-nya salah nama), dan satu-satunya assertion sungguhan di situ di-comment. Sekarang ditulis ulang: binding di-init, nama channel benar (`blue_thermal_printer/methods`), dan tiga test nyata memvalidasi `isOn`/`isPermissionBluetoothGranted`/`getBondedDevices` lewat mock `MethodChannel`.
- Repo sekarang punya `analysis_options.yaml` (`package:flutter_lints/flutter.yaml`) yang mengecualikan `example/**` — jadi kalau `flutter analyze`/`flutter test` dijalankan dari root plugin ini, folder `example/` (project Flutter terpisah dengan pubspec/lockfile sendiri) gak ikut dianalisis dan gak bikin gagal palsu.
- Konstanta `PrinterCommands.TRANSMIT_DLE_*` (query status real-time ESC/POS, `DLE EOT n`) dulu didefinisikan tapi gak pernah dipakai (dead code, gak pernah ditulis ke socket). Sekarang dipakai lewat method baru `queryPrinterStatus(int statusType)` di kedua sisi (native + Dart) -- lihat bagian Arsitektur di atas untuk mekanisme mailbox-nya.

**Masih terbuka / belum diperbaiki** — sengaja belum disentuh:
- Izin lokasi (`ACCESS_FINE_LOCATION`/`ACCESS_COARSE_LOCATION`) tetap diminta `getBondedDevices()` walau sebenarnya membaca daftar perangkat yang sudah dipasangkan gak butuh izin itu di Android — ini sengaja dipertahankan oleh konsumer yang sekarang buat rencana fitur active-discovery ke depan, bukan karena secara teknis wajib buat baca bonded devices.
- Blok `buildscript { classpath 'com.android.tools.build:gradle:3.5.4' }` di `android/build.gradle` kelihatan usang dibanding `compileSdkVersion 36` di file yang sama, tapi kemungkinan besar gak benar-benar dipakai saat plugin dikonsumsi sebagai submodule (versi AGP didikte `build.gradle`/`settings.gradle` level konsumer `parkways_valet`, bukan file ini). Belum diubah — butuh verifikasi terpisah terhadap build konsumer sebelum disentuh.
- `queryPrinterStatus` baru dites lewat tipe 2 (`TRANSMIT_DLE_OFFLINE_PRINTER_STATUS`, dipakai konsumer `parkways_valet` untuk kertas/cover/error). Tipe 1/3/4 (`TRANSMIT_DLE_PRINTER_STATUS`/`TRANSMIT_DLE_ERROR_STATUS`/`TRANSMIT_DLE_ROLL_PAPER_SENSOR_STATUS`) tersedia di channel yang sama tapi belum ada consumer maupun pengujian hardware nyata yang memverifikasinya. Printer clone murah juga gak dijamin mengimplementasikan `DLE EOT` sama sekali -- kembalikan `null` (timeout) diperlakukan sebagai "tidak diketahui", bukan galat, justru karena itu.
- `PrinterBackendSunmi.checkStatus()`/`updatePrinterState()` pada klon AIDL Xchengtech (`com.xcheng.printerservice`) terbukti membaca cache basi saat dipanggil "dingin" -- lihat catatan lengkap di bagian "API umum lintas vendor" di atas. Belum ada perbaikan sisi plugin untuk kasus spesifik ini (server tidak menyediakan cara memaksa refresh sensor tanpa lewat `printBitmap()`); mitigasinya sekarang ada di app konsumen (UI tidak lagi mengklaim "sukses" cetak).

# CLAUDE.md

File ini berisi panduan untuk Claude Code (claude.ai/code) saat bekerja dengan kode di repository ini.

## Tentang project ini

Ini adalah fork internal dari paket pub.dev `blue_thermal_printer` (upstream: `kakzaki/blue_thermal_printer`), dikelola di `Bahana-Cipta-Technology/blue_thermal_printer`. API lama (`lib/blue_thermal_printer.dart`, class `BlueThermalPrinter`) **sama sekali tidak mengonsumsi SDK vendor/pabrikan printer apa pun** — semuanya dibangun dari komponen generik/universal: API Bluetooth Classic bawaan Android (`BluetoothSocket` lewat UUID SPP standar `00001101-0000-1000-8000-00805F9B34FB`) untuk koneksi, dan byte command ESC/POS (protokol terbuka, tidak terikat merek printer manapun) yang ditulis manual untuk semua data yang dikirim ke printer. Bitmap QR di-generate pakai ZXing, itu pun cuma buat rendering lokal, bukan komunikasi ke printer. Pertahankan desain API lama ini apa adanya (jangan sisipkan SDK vendor ke `BlueThermalPrinterPlugin.java`/`BlueThermalPrinter` yang sudah ada).

> **Arah baru (lihat juga bagian "API umum lintas vendor" di bawah):** repo ini sekarang jadi *source of truth* multi-vendor bagi semua app Bahana-Cipta-Technology yang butuh printer thermal — bukan lagi cuma ESC/POS Bluetooth generik. SDK vendor (Sunmi built-in printer jadi yang pertama, sudah produksi) ditambahkan sebagai implementasi baru di belakang kontrak `PrinterBackend`, **bukan** disatukan ke kode ESC/POS/Bluetooth yang sudah ada — tiap vendor tetap terisolasi di modul/folder native-nya sendiri (lihat konvensi `vendor/<nama>/` di bagian Arsitektur) supaya build, test, dan siklus hidup satu vendor tidak terikat ke vendor lain. Keputusan ini sengaja mengubah batasan lama di paragraf sebelumnya (yang melarang SDK vendor sama sekali) — alasannya: semua app konsumen plugin ini butuh akses SDK vendor yang sama, jadi mendefinisikan kontraknya sekali di sini menghindari duplikasi/drift antar app.

Repo ini dipakai app `parkways_valet` (Flutter) lewat **git submodule + `path:` dependency** (bukan dipublish ke pub.dev). Migrasi ke kontrak baru `PrinterBackend` (lihat bagian di bawah) **sudah selesai** -- app konsumen sekarang mengimpor `package:blue_thermal_printer/printer_backend.dart` saja, tidak lagi menyentuh `blue_thermal_printer.dart` (API lama) secara langsung di mana pun. API lama tetap dipertahankan di repo ini apa adanya untuk kompatibilitas mundur (dipakai secara internal oleh `PrinterBackendEscpos`, lihat di bawah), bukan karena masih dikonsumsi langsung.

## API umum lintas vendor (`PrinterBackend`)

`lib/printer_backend.dart` adalah barrel export kontrak baru, jadi API utama yang dipakai app konsumen (API lama `blue_thermal_printer.dart` tetap dipertahankan apa adanya untuk kompatibilitas mundur, tidak dihapus). Isinya:

- `PrinterBackend` (`lib/src/printer_backend.dart`) — satu interface yang menyatukan pemasangan/koneksi perangkat *dan* pengiriman cetak (sengaja digabung, bukan dipisah seperti draf awal `PrinterService`/`PrinterConnectionService` di app konsumen), supaya backend tanpa konsep pemasangan (mis. printer bawaan) tidak perlu jawaban stub yang menyesatkan untuk method pemasangan — lihat getter `requiresPairing`.
- `PrinterDevice`, `PrinterStatus`, `Receipt`/`ReceiptLine` (`lib/src/`) — tipe data pendukung, netral terhadap vendor maupun app konsumen. `PrinterStatus.problemMessage` memetakan `hasPaper`/`coverClosed`/`hasError` jadi satu pesan Indonesia siap tampil, dipakai bersama oleh kedua implementasi di bawah supaya pesan galat konsisten lintas vendor.
- `PrinterResult`/`PrinterOk`/`PrinterErr`/`PrinterFailure` (`lib/src/result.dart`) — tipe hasil operasi milik plugin ini sendiri, terpisah dari `Result`/`Failure` app konsumen mana pun (plugin generik lintas app, tidak boleh tahu taksonomi galat satu app tertentu).
- `PrinterVendor` + `createPrinterBackend` (`lib/src/printer_vendor.dart`) — *source of truth* vendor mana saja yang plugin ini dukung, plus factory yang membangun instance `PrinterBackend` konkretnya. Ini yang dipakai app konsumen untuk memilih backend (bukan mendefinisikan enum vendor sendiri) — lihat bagian "Menambah vendor baru" di bawah.

**Perluasan kontrak (sudah diimplementasikan, terverifikasi di device testing 01):** `doc/contract-extensions-design.md`. Isinya:
- `printReceipt` → `PrintDelivery` (`confirmed`/`unverified`);
- `capabilities()`;
- `preview(Receipt)`;
- `ensureConnected({lastDevice})`.

Dokumen itu juga memuat audit sumber resmi tiap vendor. Beberapa hal yang perlu diingat:
- `getPrinterPaper()` Sunmi mengembalikan 0 = 80 mm dan 1 = 58 mm, dan hanya dipercaya dari paket Sunmi asli.
- Method itu dipanggil lewat raw transact (`WoyouTransactions`), karena proxy AIDL bawaan mengabaikan hasil `transact`: firmware tanpa method itu, termasuk klon Xcheng yang terverifikasi di O1, akan terbaca 0 = 80 mm.
- `preview` dan `printReceipt` wajib memakai renderer yang sama (`_rendererFor`/`_printRenderer`).
- `confirmed` hanya boleh muncul bila `capabilities().confirmsPrint == true`. Invariant ini dijaga oleh suite kontrak.

Vendor baru wajib mengisi keempat member ini.

**Status saat ini: kontrak + empat implementasi (ESC/POS, Sunmi, Xcheng, iMin), dipakai app konsumen.** iMin belum diverifikasi di hardware. Pemilihan printer bawaan: `detectBuiltInPrinterVendor()` (`lib/src/printer_vendor.dart`) mengecek **Xcheng, lalu iMin, lalu Sunmi**. Servis Xcheng juga menyediakan AIDL kompatibel Sunmi, jadi urutan terbalik salah mengenali perangkat Xcheng; iMin ikut dicek sebelum Sunmi dengan alasan yang sama. Fungsi ini mengembalikan `null` bila tidak ada printer bawaan. App konsumen memakainya sekali di boot dan hanya untuk default instalasi baru / belum pernah memilih -- pilihan tersimpan tidak pernah diganti otomatis.
- `PrintJobGate` (`lib/src/print_job_gate.dart`) — busy-lock + timeout 30 dtk bersama untuk `printReceipt` semua backend: pekerjaan kedua ditolak selama yang pertama berjalan, timeout Dart tidak melepas kunci sebelum pekerjaan native selesai, dan pekerjaan yang masih macet 30 dtk setelah timeout memanggil `onStuck` lalu kunci dilepas paksa. Vendor baru wajib memakainya, jangan menulis busy-flag sendiri.
- `PrinterBackendEscpos` (`lib/src/printer_backend_escpos.dart`) — membungkus `BlueThermalPrinter` (API lama) untuk printer Bluetooth generik lewat ESC/POS. `_send()` melakukan pre-check status sebelum menulis, lalu post-check setelah menulis (`checkStatus()`, ESC/POS `DLE EOT 2`, byte divalidasi lewat `PrinterStatus.tryFromOfflineStatusByte`) -- kalau post-check melaporkan masalah, tulis satu reset buffer tambahan (`ESC @`, byte `[27, 64]`) sebagai best-effort sebelum melaporkan galat ke pemanggil. `connect()` single-flight (panggilan bersamaan berbagi satu percobaan native); `onStuck` gate = `disconnect()` supaya write native yang macet terlepas. Printer yang tidak pernah menjawab query status (2 query beruntun tanpa jawaban sejak terhubung, mis. `RPPInnerPrinter`) tidak ditanya lagi sampai `connect()`/`disconnect()` berikutnya -- tanpa ini tiap cetak membayar 2× timeout native (±3 dtk).
- `PrinterBackendSunmi` (`lib/src/printer_backend_sunmi.dart`) — printer bawaan lewat AIDL kompatibel Sunmi/Woyou. Native-nya terisolasi total di `android/src/main/java/id/kakzaki/blue_thermal_printer/vendor/sunmi/` (`SunmiPrinterBridge.java`, `SunmiPrinterChannel.java`, method channel `blue_thermal_printer/sunmi`, terpisah dari channel API lama `blue_thermal_printer/methods`), tidak menyentuh logic ESC/POS di `BlueThermalPrinterPlugin.java`. Channel: `bind`/`unbind`/`updateState`/`printTransaction`. Kode status dipetakan oleh fungsi murni `sunmiStateToStatus()` sesuai tabel resmi AIDL (1 normal, 2 memperbarui, 3 gagal baca status, **4 kertas habis**, 5 overheat, 6 cover terbuka, 7 cutter abnormal, 8 cutter pulih, 505 tidak terdeteksi, 507 upgrade firmware gagal). Cetak = satu **transaksi buffer** di native (`enterPrinterBuffer(true)` → `printBitmap` → `lineWrap` → `exitPrinterBufferWithCallback`) yang menghasilkan `SunmiPrintOutcome` `printed`/`failed`/`unknown` dari `onPrintResult` -- beda dari `onRunResult` `printBitmap` polos yang menurut doc `ICallback` cuma menandakan API diterima, bukan struk tercetak. `unknown` (firmware/klon tanpa callback transaksi, atau timeout 12 dtk) jatuh ke post-check status. Callback transaksi hanya ditunggu bila AIDL disediakan paket Sunmi asli (`woyou.aidlservice.jiuiv5`, dicek dari `ComponentName` di `onServiceConnected`); klon (mis. `com.xcheng.printerservice`) langsung commit polos, dan setelah satu kali timeout pun bridge berhenti menunggu di sisa sesi.
- `PrinterBackendFallback` (`lib/src/printer_backend_fallback.dart`) — komposisi primary → fallback yang pindah **hanya saat `connect()` primary gagal**; setelah itu semua panggilan diteruskan ke backend aktif. Sengaja tidak ada fallback per cetakan (cetak yang ditolak primary karena kertas habis lalu dikirim lewat fallback yang buta kertas = data menumpuk di buffer servis). `createPrinterBackend(PrinterVendor.innerXcheng)` = `PrinterBackendFallback(primary: PrinterBackendXcheng(), fallback: PrinterBackendSunmi())`.
- `PrinterBackendXcheng` (`lib/src/printer_backend_xcheng.dart`, primary untuk `PrinterVendor.innerXcheng`) — untuk perangkat Xcheng. Memakai antarmuka native servis Xcheng (`com.xcheng.printerservice.IPrinterService`), bukan AIDL kompatibel Sunmi-nya: pre-check lewat sensor kertas `printerPaper()` (sekaligus mencegah struk menumpuk di buffer servis selama kertas habis) dan hasil cetak dari callback `onComplete()`/`onException()` `printBitmap`; tanpa callback dalam 10 dtk → sensor kertas yang menentukan. Native di `vendor/xcheng/` (`XchengPrinterBridge`, `XchengPrinterChannel`, channel `blue_thermal_printer/xcheng`) memanggil `IBinder.transact` langsung, **tanpa file AIDL**: Xcheng tidak menerbitkan SDK (integrasi resminya file AIDL yang dibagikan OEM perangkat), dan urutan method hanya konsisten antar varian firmware untuk kode 1–17 (terverifikasi dari bytecode servis perangkat uji O1 + AIDL OEM Positivo L300) -- bridge sengaja hanya memakai `printWrapPaper`=6, `printBitmap`=10, `printerPaper`=17 dan callback `onException`=1/`onComplete`=4. Servis ini tidak melaporkan cover/overheat. Sensor yang tidak menjawab = backend tidak tersedia (bukan "status unknown"), jadi suite kontrak dijalankan dengan `supportsUnknownStatus: false`. Kode native ini fork dari `sunmi_printer_plus` (lihat `LICENSE-sunmi_printer_plus` di folder yang sama).
- `PrinterBackendImin` (`lib/src/printer_backend_imin.dart`, `PrinterVendor.innerImin`) — printer bawaan iMin SDK 2.0 (D4 Pro, Swift 1 Pro/2/2 Pro/2 Ultra, Swan 2, Falcon 2). Native di `vendor/imin/` (`IminPrinterBridge`, `IminPrinterChannel`, channel `blue_thermal_printer/imin`: `bind`/`unbind`/`status`/`paperType`/`printTransaction`) memakai stub AIDL resmi `com.github.iminsoftware:IminPrinterLibrary` dari JitPack (repo disuntik plugin, lihat pengecualian di "Menambah vendor baru"). Handshake `initPrinter` → `fd` dijalankan di executor saat servis tersambung; `status` = `-1` sampai `fd` siap. Status hanya memetakan kode resmi (0 normal, 3 cover, 4 overheat, 7 kertas habis), kode lain = `unknown`. Lebar kertas (`getPrinterPaperType`) dibaca tiap cetak: 80 mm → raster 576 px + `partialCut`, selain itu 384 px. Cetak = transaksi buffer seperti Sunmi, tapi kode `onPrintResult` dilaporkan `unknown` sampai `IminPrinterBridge.PRINT_RESULT_CODE_VERIFIED` diaktifkan dari uji hardware, karena dokumen resmi iMin kontradiktif soal 0 vs 1 = sukses. Rancangan + checklist hardware: `doc/vendor-imin-design.md`.

**Hasil pengujian hardware (device testing 01: Xchengtech O1, Android 9, servis `com.xcheng.printerservice` v1.1.12, 24 Sep 2026, dengan & tanpa kertas):** AIDL kompatibel Sunmi di servis Xcheng **tidak pernah** melaporkan kertas habis (`updatePrinterState()` selalu 1) dan tidak pernah memanggil callback hasil cetak (`printBitmap`/`exitPrinterBufferWithCallback`) -- jadi `PrinterBackendSunmi` di perangkat ini tetap buta kertas walau mapping kode status sudah benar menurut spesifikasi. Printer virtual Bluetooth `RPPInnerPrinter` tidak menjawab `DLE EOT` sama sekali. Data yang dikirim saat kertas habis ditahan servis lalu tercetak menumpuk begitu kertas dipasang. Satu-satunya sinyal akurat adalah antarmuka native Xcheng (lihat `PrinterBackendXcheng`). Mitigasi UI-level app konsumen (halaman cetak struk tidak mengklaim "sukses" berdasarkan `PrinterOk` semata) tetap dipertahankan untuk backend default.

### Menambah vendor baru (mis. Epson, PAX, iMin)

Pola yang sudah dipakai (`PrinterBackendSunmi`/`PrinterBackendXcheng`) jadi cetakan untuk vendor berikutnya. Rancangan konkret vendor berikutnya (iMin SDK 2.0 lewat library resmi `IminPrinterLibrary` dari JitPack, diperbarui 25 Sep 2026) ada di `doc/vendor-imin-design.md`.
1. Native: modul terisolasi baru di `android/.../vendor/<nama>/`, method channel sendiri (`blue_thermal_printer/<nama>`), tidak menyentuh kode vendor lain.
2. Dart: class baru `PrinterBackend<Nama>` di `lib/src/`, implementasi `PrinterBackend` sepenuhnya (termasuk pre-check status kalau SDK vendor menyediakannya).
3. Daftarkan di `PrinterVendor` (`lib/src/printer_vendor.dart`) -- satu nilai enum baru plus satu case di `createPrinterBackend`, dijaga *exhaustive* oleh compiler Dart supaya tidak ada tempat lupa di-update yang lolos diam-diam.
4. Test dengan constructor-injected fakes (pola `printer_backend_sunmi_test.dart`/`printer_backend_escpos_test.dart`), **wajib** termasuk `runPrinterBackendContract('<Nama>', …)` dari `test/support/printer_backend_contract.dart` (invariant lintas vendor: tidak kirim data saat tidak terhubung/pre-check gagal, `unknown` tidak memblokir, busy-lock, timeout, hard-timeout, dependency yang melempar tidak bocor). Pakai `PrintJobGate` untuk `printReceipt`. Lalu verifikasi behavior native ke hardware fisik lewat app konsumen (`flutter build apk --debug`) -- `flutter test` di repo ini tidak bisa memverifikasi hardware sungguhan.

Sebelum mem-fork SDK vendor manapun: cek dulu lisensi source yang jadi referensi (community plugin pub.dev sering MIT, boleh dipakai sebagai titik awal fork) dan **jangan** langsung menambah `dependency:` ke package pihak ketiga di `pubspec.yaml` -- pola repo ini adalah isolasi native per vendor di dalam plugin sendiri (lihat poin 1), bukan menumpuk dependency eksternal yang siklus hidup/maintenance-nya di luar kendali kita.

**Pengecualian: artefak native resmi vendor lewat Maven.** Library Android resmi yang diterbitkan vendor sendiri (mis. `com.github.iminsoftware:IminPrinterLibrary`) boleh dipakai sebagai `implementation` di `android/build.gradle`. Syaratnya:
- versi dipatok tepat;
- dipakai hanya dari dalam `vendor/<nama>/`;
- repo non-standar (mis. JitPack) disuntik plugin lewat blok `rootProject.allprojects { repositories { … } }` dengan `content { includeGroup '<group vendor>' }`.

Gradle me-resolve dependency plugin memakai repo milik app, jadi tanpa penyuntikan ini tiap app konsumen harus mengedit Gradle-nya sendiri. Konsekuensinya didokumentasikan di doc vendor terkait:
- build app butuh akses ke repo tersebut;
- app yang memakai `dependencyResolutionManagement` dengan `FAIL_ON_PROJECT_REPOS`/`PREFER_SETTINGS` harus menambah repo itu sendiri.

Larangan menambah dependency pihak ketiga di `pubspec.yaml` tetap berlaku.

**Dukungan platform pada praktiknya cuma Android.** `ios/Classes/SwiftBlueThermalPrinterPlugin.swift` dan versi macOS-nya itu cuma stub registrasi yang mengabaikan `call.method` sepenuhnya — apa pun method yang dipanggil, dia selalu balikin string versi device. Artinya manggil apa pun (`isOn`, `connect`, dst) di iOS/macOS bakal balikin `String` padahal yang diharapkan `bool`/list/dst, dan bakal error/cast exception di sisi Dart. Anggap iOS/macOS **tidak fungsional** — tabel platform di README (yang menandai semua platform selain Android sebagai tidak didukung) itu yang benar. `pubspec.yaml` tidak lagi mendaftarkan plugin class untuk `ios`/`macos` (dihapus supaya metadata tooling konsisten dengan status "tidak fungsional" ini); kalau dua platform itu suatu saat diimplementasikan sungguhan, daftarkan lagi entrinya di `flutter.plugin.platforms`.

## Arsitektur

Satu `MethodChannel` (`blue_thermal_printer/methods`) untuk semua pemanggilan request/response, plus dua `EventChannel`: `.../state` (broadcast adapter Bluetooth + status ACL connect/disconnect, diekspos lewat `onStateChanged()`) dan `.../read` (byte yang dibaca balik dari `InputStream` printer, diekspos lewat `onRead()`). Sisi Dart (`lib/blue_thermal_printer.dart`) itu singleton (`BlueThermalPrinter.instance`), bukan class static murni.

Semua logic native ESC/POS ada di `android/src/main/java/id/kakzaki/blue_thermal_printer/BlueThermalPrinterPlugin.java` (satu `switch` besar berdasarkan `call.method` di dalam `onMethodCall`), plus helper — `PrinterCommands.java` (konstanta byte ESC/POS mentah: align, feed, potong kertas, buka laci kasir), `Utils.java` (`decodeBitmap` → delegasi ke `RasterImageEncoder`), dan dua helper Java murni yang dites JUnit: `RasterImageEncoder.java` (piksel ARGB → `GS v 0` little-endian, pita ≤128 baris, alpha dikomposit ke putih) dan `EscPosStatus.java` (validasi pola bit respons `DLE EOT`: `(b & 0x93) == 0x12`).

Model threading yang perlu diperhatikan kalau mau menyentuh kode native:
- `connect`/`disconnect` jalan lewat `AsyncTask.execute` (background thread). Koneksi aktif disimpan di `static AtomicReference<ConnectedThread> connectedThreadRef` — cuma ada **satu** koneksi aktif di level class, bukan per instance plugin. Flag `static AtomicBoolean connecting` menolak percobaan paralel (`connect_in_progress`); `connect()` ke alamat yang sama selagi koneksi hidup langsung `success(true)` (idempoten), ke alamat lain → `already connected`.
- **Koneksi membersihkan dirinya sendiri:** saat `ConnectedThread.run()` berakhir (socket putus, stream gagal dibuka, exception apa pun), `finally`-nya `compareAndSet(this, null)` + menutup socket. Jangan kembali bergantung pada BroadcastReceiver `.../state` untuk ini -- receiver itu hanya terdaftar selama ada yang listen `onStateChanged()` (app konsumen tidak listen). Selalu ambil koneksi lewat `activeConnection()` (sekaligus membuang koneksi yang sudah mati), jangan baca `connectedThreadRef` langsung. Receiver ACL hanya memutus koneksi bila alamat perangkatnya cocok.
- Semua operasi tulis (`write`, `writeBytes`, `print*`, `paperCut`, `drawer*`) dijalankan di `static ExecutorService writeExecutor` (satu thread, serial), **bukan** platform thread -- raster struk puluhan KB lewat SPP bisa memblokir berdetik-detik (risiko ANR). Hasil dikirim lewat `MethodResultWrapper` yang mem-post ke main thread. `queryPrinterStatus` jalan lewat `AsyncTask.execute` karena harus menunggu respons hingga `STATUS_QUERY_TIMEOUT_MILLIS`.
- `ConnectedThread.run()` loop `inputStream.read()`; byte yang tidak diminta diteruskan ke `EventChannel` read lewat `emitRead()` (di-post ke main thread, syarat `EventSink`), dan **dibuang** bila tidak ada listener (`readSink` `volatile`). Dulu `readSink.success` dipanggil langsung dari thread ini, sehingga NPE saat tidak ada listener mematikan thread baca (dan semua query status sesudahnya) selamanya.
- `queryPrinterStatus` (ESC/POS `DLE EOT n`, dipetakan dari `PrinterCommands.TRANSMIT_DLE_*`) butuh menangkap satu byte respons yang datang lewat `InputStream` yang sama dengan yang terus-menerus dibaca `ConnectedThread.run()` di atas. Solusinya: mailbox satu slot (`ArrayBlockingQueue<Byte> statusResponseMailbox` + flag `awaitingStatusResponse`) di dalam `ConnectedThread` — di-*arm* lewat `armStatusRequest()` sebelum menulis command query, dan `run()` sendiri yang mencari byte **status yang sah** pertama (`EscPosStatus.indexOfRealtimeStatus`) di tiap potongan data lalu mengalihkannya ke mailbox; byte lain (XON/XOFF, sisa respons lama) tetap diteruskan ke `emitRead`. `ConnectedThread.write(byte[])` `synchronized` supaya query status dan print job tidak saling rebutan `OutputStream`.

## Known issues

**Sudah diperbaiki di fork ini** (lihat riwayat commit — perbaikan ini wajib supaya plugin bisa dipakai sama sekali oleh konsumer Dart 3.x/AGP modern, atau buat menutup bug correctness yang nyata):
- `environment.sdk` sebelumnya `>=2.12.0 <3.0.0`, gak cocok sama app Flutter modern manapun; dinaikkan ke `<4.0.0`.
- `android/build.gradle` gak punya `namespace` AGP (wajib buat AGP 8+) dan `compileSdkVersion`-nya masih 31, yang bikin gagal di pengecekan AAR-metadata terhadap versi AndroidX transitif modern; keduanya sudah dinaikkan (`compileSdkVersion 36`).
- Cabang permintaan izin Android 12+ di `getBondedDevices()` pakai `requestCode` hardcode `1`, padahal `onRequestPermissionsResult` cuma cocok sama `REQUEST_COARSE_LOCATION_PERMISSIONS` (`1451`) — `Result` yang pending gak pernah ke-resolve, jadi percobaan pertama grant izin di API 31+ hang selamanya. Sekarang kedua cabang pakai request code yang sama.
- Ditambahkan `isPermissionBluetoothGranted` (native `hasRequiredBluetoothPermissions()` + getter Dart) — cara cek status izin tanpa efek samping memicu dialog permintaan izin, sesuai kebutuhan konsumer sebelum mencoba `connect()`.
- `com.android.support:multidex` (gak dipakai, dari grup support-library pre-AndroidX yang sudah *frozen*) sudah dihapus; `androidx.appcompat`, `com.google.zxing:core`, dan `com.journeyapps:zxing-android-embedded` sudah dinaikkan ke versi terbaru.
- `ConnectedThread.write(byte[])` dulu menelan `IOException` secara internal (cuma `printStackTrace()`, gak dilempar lagi), jadi `writeBytes`/`write`/`print*` di plugin ini manggil `result.success(true)` **tanpa syarat**, bahkan pas penulisan fisik ke socket-nya gagal. Sekarang `write(byte[])` mengembalikan `boolean` dan tiap pemanggil (semua method yang menulis ke printer) memeriksa hasilnya lewat helper `writeOrFail(...)`, mengembalikan `result.error("write_error", ...)` kalau tulis fisik gagal.
- `onRequestPermissionsResult` dulu cuma cek `grantResults[0]`, bukan seluruh array — grant sebagian (misal `BLUETOOTH_SCAN` diizinkan tapi `BLUETOOTH_CONNECT` ditolak) tetap dianggap granted penuh. Sekarang mensyaratkan semua elemen `grantResults` granted.
- Dulu gak ada timeout di sekitar pemanggilan blocking `socket.connect()`; device yang gak respon bisa bikin percobaan connect hang tanpa batas waktu. Sekarang dibungkus `ExecutorService`/`Future.get(CONNECT_TIMEOUT_MILLIS, ...)` (12 detik) yang menutup socket dan mengembalikan `result.error("connect_timeout", ...)` kalau kelamaan.
- Dulu gak ada fallback reflection ke `createRfcommSocket(1)` (channel 1) pas socket RFCOMM secure standar gagal — workaround yang dikenal luas di ekosistem Android BT Classic buat bug "read failed, socket might closed" yang muncul di sejumlah kombinasi device/printer. Sekarang dicoba otomatis (`attemptFallbackConnect`) begitu percobaan standar melempar exception (bukan saat timeout).
- File test bawaan `test/blue_thermal_printer_test.dart` dulu gagal kalau dijalankan (`setMockMethodCallHandler` dipanggil tanpa `TestWidgetsFlutterBinding.ensureInitialized()` duluan, dan channel-nya salah nama), dan satu-satunya assertion sungguhan di situ di-comment. Sekarang ditulis ulang: binding di-init, nama channel benar (`blue_thermal_printer/methods`), dan tiga test nyata memvalidasi `isOn`/`isPermissionBluetoothGranted`/`getBondedDevices` lewat mock `MethodChannel`.
- Repo sekarang punya `analysis_options.yaml` (`package:flutter_lints/flutter.yaml`) yang mengecualikan `example/**` — jadi kalau `flutter analyze`/`flutter test` dijalankan dari root plugin ini, folder `example/` (project Flutter terpisah dengan pubspec/lockfile sendiri) gak ikut dianalisis dan gak bikin gagal palsu.
- Konstanta `PrinterCommands.TRANSMIT_DLE_*` (query status real-time ESC/POS, `DLE EOT n`) dulu didefinisikan tapi gak pernah dipakai (dead code, gak pernah ditulis ke socket). Sekarang dipakai lewat method baru `queryPrinterStatus(int statusType)` di kedua sisi (native + Dart) -- lihat bagian Arsitektur di atas untuk mekanisme mailbox-nya.
- **Audit September 2026** (detail lengkap + checklist verifikasi hardware di `doc/audit-2026-09.md`): mapping status Sunmi 3/4 (K1); thread baca ESC/POS mati saat tidak ada listener `onRead()` (K2); koneksi basi yang membuat reconnect mustahil (K3); header raster `Utils.decodeBitmap` rusak untuk gambar ≥256 px + piksel transparan tercetak hitam (K4); hasil cetak Sunmi kini dari `onPrintResult` transaksi (T1); validasi byte `DLE EOT` (T2); write ESC/POS dipindah dari platform thread (T3); race connect (T4); kunci "masih memproses" permanen (T5, `PrintJobGate`); `ReceiptRenderer` menolak lebar bukan kelipatan 8 (T6); binding Sunmi (`onBindingDied`/`onNullBinding`, polling connect ±3 dtk) (T7).
